# 1. PRODUCT

## Name

**AgentGuard**

## Tagline

**Memory-Powered Supervision for AI Agents**

## Core idea

AgentGuard is an AI supervision platform where:

**A Worker AI Agent performs a task → a Supervisor AI reviews it → relevant past experiences are retrieved from long-term memory → human corrections are remembered → future similar mistakes can be detected and prevented.**

The central learning loop is:

**Observe → Correct → Remember → Retrieve → Prevent**

This is NOT just a chatbot with memory.

It is a system for supervising AI agents and learning from their previous failures.

# 4. WORKER AGENT

Create a Worker Agent called:

**Support Agent**

Responsibilities:

1. Receive customer request.
2. Understand the request.
3. Identify the relevant support category.
4. Retrieve relevant company policies.
5. Retrieve relevant previous experiences when appropriate.
6. Generate a proposed response.
7. Send the proposed response to the Supervisor.
8. Receive Supervisor feedback.
9. Revise the response when necessary.
10. Produce the final response.

The Worker Agent should be a real LLM-powered component.

Do not implement a giant collection of hardcoded `if/else` responses.

# 5. SUPERVISOR AGENT

Create a separate AI component:

**AgentGuard Supervisor**

The Supervisor must independently review the Worker Agent's proposed response.

It must evaluate:

### Policy compliance

Does the response follow the available company policy?

### Accuracy

Does the response make unsupported claims?

### Missing information

Does the agent need additional information from the customer?

### Risk

Could the response create a customer/business problem?

### Historical failures

Does the current situation resemble a previous agent failure?

### Human corrections

Has a human previously corrected a similar situation?

### Consistency

Does the response contradict known policy or previous approved guidance?

The Supervisor should return structured data.

Use a schema similar to:

```json
{
  "status": "SAFE",
  "risk_level": "LOW",
  "policy_issues": [],
  "memory_matches": [],
  "reason": "The response follows the refund policy.",
  "recommended_action": "Proceed",
  "confidence": 0.92
}
```

Allowed status values:

* SAFE
* REVIEW_REQUIRED
* PREVIOUS_FAILURE_DETECTED

Allowed risk:

* LOW
* MEDIUM
* HIGH

Do NOT expose hidden chain-of-thought.

Only display a concise explanation/evidence to the user.

# 6. HINDSIGHT MEMORY

Use Hindsight as the long-term memory layer if available.

The application should store meaningful experiences rather than blindly saving every conversation.

Each important experience should contain structured information such as:

```json
{
  "domain": "customer_support",
  "category": "refund",
  "situation": "...",
  "customer_request": "...",
  "agent_response": "...",
  "failure": "...",
  "human_correction": "...",
  "correct_action": "...",
  "outcome": "...",
  "severity": "medium",
  "policy_reference": "...",
  "timestamp": "..."
}
```

Memory retrieval must be semantic/contextual.

Do NOT rely only on exact string matching.

For example:

Previous case:

> Customer asked for a refund after 45 days.

Later case:

> Customer asks whether they can get their money back after 40 days.

The system should recognize that these are related even though the wording is different.
